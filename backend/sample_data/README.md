# Sample data (entirely synthetic)

Generated by `generate_sample_data.py` (seed 1337). External addresses are RFC 5737 documentation ranges; internal hosts are RFC 1918. Nothing refers to a real system.

## `sample_security_logs.csv` (270 events, 2025-03-10 UTC)
Uses deliberately non-canonical headers (`src_ip`, `dst_ip`, `user`, `dst_port`, `bytes_out`, …) to exercise alias mapping; `resource` is kept in `additional_metadata`.

| Success after failures | `admin` login 02:15:30 from 203.0.113.50 | R-AUTH-002 (High), T1078 (potential) |
| Sensitive access | `admin` denied on /etc/shadow ×2, .ssh key, /admin/keys; /etc/passwd read succeeds (not flagged alone) | R-ACC-001 (Medium), T1003.008 (potential) |
| Egress | 10.0.1.10 → 203.0.113.99, 3 × 30 MB, user `admin` | R-NET-003 (High), T1048 (potential) |
| Correlation | The four findings above share user `admin` | R-COR-001 **Critical** |
| Password spray | 9 failures, 9 accounts, 192.0.2.77, 06:00 | R-AUTH-001, T1110.003 (potential); spray targets are not used for correlation |
| Port scan | 198.51.100.9 → 10.0.2.20, 30 ports in 90 s | R-NET-001, T1046 |

The ML detector also flags a few benign-but-rare events (e.g. erin's failed login) at Low severity. That is expected: an anomaly is not necessarily malicious.

## `sample_windows_auth.jsonl` (12 events)
Windows-style fields (`TimeCreated`, `EventID` 4624/4625, `IpAddress`, `TargetUserName`, `Computer`): 6 failures then a success for `svc_sql` from 192.0.2.201 → R-AUTH-001 + R-AUTH-002 (+ correlation). Too small for ML, so ML is skipped with an explanation; rules needing absent fields (ports, bytes, resources) are skipped and reported.

`backend/tests/test_sample_data.py` asserts these expectations so the table cannot drift from the code.
